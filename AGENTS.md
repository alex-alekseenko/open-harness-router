# Working on Open Harness Router

## Project and architecture

This is a Python 3.13 routing proxy. `routing.yaml` selects a provider by model
name; `routing.example.yaml` is the public configuration template. Native
Anthropic requests use passthrough; other providers translate Messages requests
to OpenAI Chat Completions or Responses. Codex uses native Responses forwarding
and the catalog/profile generated by `cli.sync_codex_config`; capability
metadata lives on routing rules under `codex`.
`codex_catalog_path` adds the native account catalog, and `responses_default`
provides its native inference fallback independently of the Messages default.
Native credential forwarding requires `responses_forward_client_auth: true`;
own-key custom providers must continue stripping client credentials.
Native-auth Codex profiles keep the built-in `openai` provider identity and
redirect it with `openai_base_url`, so ordinary saved sessions remain
resumable. Preserve this identity when changing profile generation.
Codex's built-in image tool uses native Images endpoints at the same base URL.
Forward these only through the explicitly authenticated Responses fallback,
never through custom-model routing rules or an own-key fallback. Preserve the
native JSON body and image request headers; do not log image data or prompts.
Custom model metadata must also carry model-specific instructions; otherwise
Codex's GPT identity fallback produces misleading self-reports. Preserve the
native model instructions and coding workflow when adapting custom identities.

- `src/main.py`: application factory and shared runtime lifecycle.
- `src/api/`: HTTP endpoints and adaptation of provider results to ASGI.
- `src/providers/`: upstream clients and provider implementations.
- `src/conversion/`: protocol translation.
- `src/routing/`: configuration schema, matching and provider registry.
- `src/proxy/`: CONNECT/TLS forward proxy; shares the provider registry.
- `src/services/`: monitoring, persistence, retries and conversation state.
- `src/cli/`: configuration, TLS and release helpers.
- `tests/unit/` and `tests/integration/`: offline tests with mocked upstreams.

Keep provider code independent of FastAPI. Use `ProviderResult` and
`ClientChannel`; release upstream resources on completion, error and client
disconnect, including streams that never start. Preserve the existing
Anthropic endpoints when adding another client protocol.

## Development and verification

Install with `uv sync`. Run `make lint`, `make typecheck` and `make test`, or
`make full-check` for all three (the same command runs in CI). Focused tests:
`uv run pytest -q tests/unit/test_<area>.py`. If the environment is already
installed, `.venv/bin/ruff`, `.venv/bin/mypy` and `.venv/bin/pytest` also work
without dependency resolution. Python imports are rooted at `src`.

Prefer small changes and verify existing APIs before using them. Add regression
tests for protocol or routing behavior. Use mocked upstreams in tests; keep
personal `.env` and `routing.yaml` out of test fixtures. Write new code,
comments and instructions in English. Update user documentation for changed
setup or behavior, and report checks and any unverified live behavior honestly.

## Local configuration and running services

`.env`, `routing.yaml`, `certs/*.pem`, `proxy-ca/`, `state/`, `.launchd-label`
and skill `references/local/` directories are machine-local and gitignored.
Never publish credentials, internal hosts, request content or private CA keys.
Use `.env.example` and `routing.example.yaml` for public examples.

`make run` serves the HTTP API on port 8787 by default; `make run-proxy` starts
both HTTP and forward-proxy listeners. Configuration is read at startup.
Validate offline before restarting a configured service. Development checks
should use an isolated port and temporary state so they do not disrupt the
router serving existing sessions.

After successfully publishing a release, restart the running local router as
part of the release workflow without asking for another confirmation. Wait for
active requests to finish before restarting. Use
`.claude/skills/add-provider/scripts/restart_router.sh`, then verify `/health`
and that `/dashboard/state` reports the released version with
`restart_required: false`. This project rule overrides the release skill's
default instruction not to restart the router.

## Existing Claude workflows

The repo has no project `CLAUDE.md`. Its reusable workflows are currently in
`.claude/skills/`. For provider onboarding, read
`.claude/skills/add-provider/SKILL.md` and its relevant references; for an
explicit release request, read `.claude/skills/release/SKILL.md`. These contain
project-specific validation, credential handling and release procedures.
The Claude permission allowlist in `.claude/settings.json` is client-specific;
Codex uses the permissions of its own session.
